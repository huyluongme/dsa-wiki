# Array

An **array** is the simplest way to keep a collection of things in order: a row of boxes, side by side, each with a number on it.

## Idea

Picture a row of numbered seats in a cinema. Every seat holds one person, the seats are right next to each other, and each seat has a number. If your ticket says seat 3, you walk straight to seat 3. You do not check seats 0, 1 and 2 first.

An array works the same way:

- The **seats** are the array's **items**. They sit side by side in the computer's memory.
- The **seat numbers** are called **indexes**. Counting starts at **0**, not 1, so an array with 5 items has indexes 0 to 4. This surprises everyone at first, and you get used to it quickly.
- You can go **straight to any item** using its index. No searching needed.

<ArrayDiagram name="scores" items={[10, 20, 30, 40, 50]} />

In code, `scores[3]` means "the item at index 3", which is `40` here.

<details>
<summary>Optional: how the computer finds a seat so fast</summary>

Because the seats are side by side, the computer only needs simple arithmetic. If the row starts at memory address `base` and each item takes `s` bytes (an `int` usually takes 4), the item at index `i` lives at:

$$
\text{address}(i) = \text{base} + i \times s
$$

For example, if `base` is 1000 and `s` is 4, index 3 is at $1000 + 3 \times 4 = 1012$. One multiplication and one addition, however big the array is.

</details>

## How it works

### Reading and changing: instant

Reading or changing `scores[3]` takes the same tiny effort whether the array has 5 items or 5 million. The computer jumps to the seat and does not look at the others.

### Inserting: everyone shifts

Say a new item, `25`, wants seat 2, but seat 2 is already taken. Seats cannot be squeezed apart, so everyone from seat 2 onward slides one seat to the right to make room. For that to work, the row needs one empty seat at the end.

The order matters: move the **last** item first. If you started at the front, you would overwrite the next item before you had copied it.

```text
position:             0     1     2     3     4     5
start:               10    20    30    40    50     _
move 50 right:       10    20    30    40    50    50
move 40 right:       10    20    30    40    40    50
move 30 right:       10    20    30    30    40    50
put 25 in:           10    20    25    30    40    50
```

With 5 items that is quick. With a million items, up to a million of them have to move. So inserting near the **front** is slow, while inserting at the **end** is fast, because nobody has to move.

### Deleting: close the gap

An array cannot keep an empty seat in the middle. When an item leaves, everyone after it slides one seat to the left.

```text
position:             0     1     2     3     4
start:               10    20    30    40    50
move 30 left:        10    30    30    40    50
move 40 left:        10    30    40    40    50
move 50 left:        10    30    40    50    50
shrink by one:       10    30    40    50
```

It is the same story as inserting: deleting near the front means many moves, deleting at the end means none.

### Searching: look one by one

If you know the index, reading is instant. But if you only know the **value**, for example "where is 40?", the computer has no shortcut. It checks seat 0, then seat 1, then seat 2, and so on until it finds 40. For a big array that can take a while. (If the items are sorted, there is a much faster trick called binary search. It gets its own page later.)

### When the row is full: growable arrays

A basic array has a fixed number of seats, decided when you create it. What if you need more?

Most languages offer a **growable array** (also called a dynamic array): `list` in Python, `std::vector` in C++, `ArrayList` in Java. When the row is full, it builds a new row twice as long, moves everyone over, and throws the old row away. C has no ready-made one, so you do it yourself with `malloc` and `realloc`, as the code below shows.

Moving everyone is slow, but it happens rarely. After the row doubles, there is plenty of free room, so you can add many items before the next move. So **on average**, adding to the end is still fast.

<details>
<summary>Optional: why "on average" is fast</summary>

Add $n$ items one by one to an empty growable array that doubles when full. Moves happen when the size reaches 1, 2, 4, 8, ... and the total number of items moved is:

$$
1 + 2 + 4 + \dots + 2^k = 2^{k+1} - 1 < 2n \qquad (2^k < n)
$$

That is fewer than 2 moves per added item, so the extra cost per item is a small constant. This is called **amortized** $O(1)$.

</details>

### Insert and delete by shifting

Here the array has room for 6 items but only 5 are in use, and `size` keeps track of that. To keep the code short, these functions assume the index is valid and there is room for one more item. Real code should check both.

<Tabs groupId="language">
  <TabItem value="c" label="C" default>

```c title="insert_remove.c"
#include <stdio.h>

// Put value at index pos. Returns the new size.
int insert_at(int arr[], int size, int pos, int value) {
    for (int i = size; i > pos; i--) {
        arr[i] = arr[i - 1];  // shift right, last item first
    }
    arr[pos] = value;
    return size + 1;
}

// Remove the item at index pos. Returns the new size.
int remove_at(int arr[], int size, int pos) {
    for (int i = pos; i < size - 1; i++) {
        arr[i] = arr[i + 1];  // shift left, first item first
    }
    return size - 1;
}

int main(void) {
    int arr[6] = {10, 20, 30, 40, 50};  // room for 6, 5 in use
    int size = 5;

    size = insert_at(arr, size, 2, 25);  // 10 20 25 30 40 50
    size = remove_at(arr, size, 0);      // 20 25 30 40 50

    for (int i = 0; i < size; i++) printf("%d ", arr[i]);
    printf("\n");
    return 0;
}
```

### A growable array

In C you manage the growing yourself: ask for memory with `malloc`, get a bigger block with `realloc` when the row is full, and give the memory back with `free`. (To keep it short, the code does not check whether `malloc` and `realloc` succeeded. Real code should.) The other languages do all of this for you. In the code below, the operations marked "slow" are the ones that make the other items shift, as you saw above.

<Tabs groupId="language">
  <TabItem value="c" label="C" default>

```c title="growing.c"
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    int capacity = 2;  // seats in the row
    int size = 0;      // seats taken
    int *nums = malloc(capacity * sizeof(int));  // ask for 2 seats

    for (int i = 1; i <= 5; i++) {
        if (size == capacity) {  // the row is full
            // get a row twice as long and move everyone over
            capacity *= 2;
            nums = realloc(nums, capacity * sizeof(int));
        }
        nums[size] = i * 10;  // add the new item at the end
        size++;
    }

    // print every item: 10 20 30 40 50
    for (int i = 0; i < size; i++) printf("%d ", nums[i]);
    printf("\n");

    free(nums);  // give the memory back when you are done
    return 0;
}
```

## Complexity

Complexity answers one question: **if the array gets bigger, how much slower does this operation get?** Two terms are enough for now:

- **O(1)**: instant. The same effort whether the array has 10 items or 10 million.
- **O(n)**: the effort grows in step with the number of items, called **n**. Twice as many items means roughly twice the work.

| Operation                              | Cost        | In plain words                                                       |
| -------------------------------------- | ----------- | -------------------------------------------------------------------- |
| Read or change the item at an index    | $O(1)$      | Jump straight to the seat.                                           |
| Add or remove at the end               | $O(1)$      | Nobody has to move. A growable array is slow only when it must grow. |
| Insert or remove at the front or middle | $O(n)$     | Everyone after that seat has to slide over.                          |
| Find a value in an unsorted array      | $O(n)$      | Check the seats one by one. In the worst case, all of them.          |
| Find a value in a sorted array         | $O(\log n)$ | Binary search. Doubling the items adds only one more step.           |
| Memory used                            | $O(n)$      | One seat per item.                                                   |

## When to use it

An array is a great fit when:

- You read items by their position, like the days of the week, the pixels of an image, or the scores of a game.
- You go through all the items in order.
- You mostly add and remove at the end, like a shopping cart.
- You want speed. Items sit side by side in memory, which computers handle very efficiently.

Look at another structure when:

- You often insert or remove at the front or middle. A linked list or a deque fits better.
- You look items up by a name or key instead of a position. A hash table is much faster at that.

:::warning[Common mistakes]
- **Off by one.** An array with 5 items has indexes 0 to 4. `scores[5]` does not exist.
- **No safety net in C and C++.** Going past the end does not raise an error. The program reads or writes whatever happens to be next to the array. It may crash, or quietly give wrong answers.
- **Slow loops.** Inserting or removing at the front inside a loop makes everyone shift every time, so a fast program becomes a slow one.
:::
